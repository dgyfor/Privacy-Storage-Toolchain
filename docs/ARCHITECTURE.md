# 系统架构思路

## 一、核心痛点
现有的云端存储要么完全明文（隐私泄露），要么加密后原始文件名和目录结构被破坏（变成一堆乱码哈希，导致文件找不到、无法确认原貌）。我的目标是：让隐私文件在云端是绝对安全的密文，但在本地管理界面上是清晰可见、可检索的原貌。

## 二、技术方案
1. 端侧加密（Bash/OpenSSL）：利用安卓端 Termux 环境，写 Bash 脚本调用 OpenSSL，实现本地文件批量 AES-256-CBC 加密。加密后的文件重命名为随机串，但在本地生成并维护一份映射索引（记录原文件名、加密后文件名、真实存放路径）。
2. 可视化映射（原生JavaScript）：用原生 HTML/CSS/JS 开发一套多网盘可视化树状管理系统（SPA）。前端读取本地索引，把散落在本地/云盘A/云盘B的加密文件，映射成用户能看懂的树状结构。
3. 容灾保障（PAR2）：针对云盘存储可能发生文件损坏的情况，整合 PAR2 冗余恢复脚本，实现“加密 -> 存储 -> 损坏 -> 一键恢复 -> 解密”的完整闭环。

## 三、系统架构（分五层）
输入层（本地/云盘A/云盘B） -> 加密层（Bash+OpenSSL批量加密） -> 映射层（原生JS树状可视化+本地索引） -> 容灾层（PAR2恢复脚本） -> 展示层（如日记网站作为元数据轻量级展示）。

## 四、演示闭环
答辩时现场演示：放入文件 -> 一键加密 -> 分发到多盘 -> 界面可视化检索原文件名 -> 模拟文件损坏 -> PAR2恢复 -> 解密还原原文件。以此证明这不是一个孤立的HTML或脚本，而是一套完整的隐私文件工具链。
## 五、 跨环境协同架构设计（关键工程设计）

本系统在真实的安卓开发环境中面临一个工程限制：MT管理器拥有友好的文件选择交互界面，但其底层环境无法安装 PAR2 命令行依赖；而 Termux 终端可以完美运行 PAR2 库，但交互体验极差。

基于“各司其职、解耦设计”的原则，本系统采用了跨环境协同架构：
1. **加密模块**：运行于 MT管理器环境，专注利用 Bash/OpenSSL 完成端侧加密，并生成唯一的通信桥梁 `index.json` 索引文件。
2. **容灾模块**：独立运行于 Termux 环境，通过读取 `index.json` 中的加密文件列表与路径信息，执行 PAR2 批量生成与修复。
3. **通信机制**：两个环境不直接调用，完全依靠 `index.json` 作为数据契约进行通信，保证了模块的独立性与系统的健壮性。
